# Runtime memory incident and recovery

On 2026-10-18, authorized Render logs confirmed a web-process crash at 22:23:57 UTC: `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`. The last GC reported about 251 MB of live heap. Public requests then returned HTTP 502 with `x-render-routing: no-deploy` while the process restarted. The service runs on the existing free 512 MB instance.

Read-only production database measurements identified 2,022 current canonical work units across 47 source documents. The dependency-readiness query repeated the entire source body for every unit: 154,271,969 bytes of plan text, compared with 1,932,891 bytes when read once per repository. This excludes PostgreSQL driver buffers, parsed objects and the rest of the application. This amplification provides a concrete explanation for heap exhaustion on dashboard requests.

The recovery loads compact unit rows separately from source documents, reads each document once, and evaluates the shared dependency graph once for the portfolio. An iterative strongly connected component evaluation preserves cycle, missing-source, release-inclusion and unresolved prerequisite failures. Shared graph paths are not expanded exponentially and deep plans do not exhaust the JavaScript call stack. Every unit, PR fact, source fingerprint and runtime declaration remains in scope; no denominator is truncated and no readiness is fabricated.

Regression gates include a real PostgreSQL 210-unit source payload and transfer-byte assertion, shared dependency graph and 6,000-unit chain tests, cyclic failure propagation, and authenticated browser counters against a large 210-unit document. The browser web server is capped at a 256 MB Node heap to reproduce the observed resource constraint. Existing counts, dependency acceptance, login, access controls, and desktop/mobile browser journeys remain required.

Render separately canceled the 22:24:55 UTC deployment because the workspace had exhausted build pipeline minutes. The owner subsequently reported raising the existing monthly build spend limit to $7, with $5 spent. Do not raise that limit, upgrade compute or add paid resources. Use GitHub Actions for all verification and merge only after it succeeds; the merge triggers the existing Render service's automatic deployment. Do not start redundant Render builds. Confirm the actual deploy reaches `live`, then verify its exact commit, readiness, public access routing and subsequent runtime logs before reporting recovery. A running old build or green CI alone is insufficient.

If the provider still rejects builds under the owner's existing limit, preserve that exact error and report the concrete remaining limit. Build credits and application runtime are separate; do not describe pipeline exhaustion as the cause of an out-of-memory process exit.
